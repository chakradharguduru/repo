# Repo RAG — ask questions about your codebase

A small, file-per-concern RAG project: it reads your repo, splits Python
files into function/class-level chunks, embeds them, and lets you ask
questions in plain English. Answers are generated by an open-source LLM
(Llama 3.1, served via Groq's free API) and grounded in the actual code
retrieved.

## How the pieces fit together

```
config.py        <- edit settings here (repo path, model names, etc.)
ingest.py         -> walks the repo, splits files into chunks
embed_index.py     -> turns chunks into vectors, builds/saves/loads the FAISS index
search.py           -> given a query, filters + finds the closest chunks
llm.py               -> sends chunks + query to Groq, gets back an answer
rag_agent.py          -> combines search.py + llm.py into one ask() call
main.py                -> the CLI you actually run
```

If you want to change *what* gets indexed → edit `ingest.py`.
If you want to change *which* LLM answers → edit `llm.py` only.
If you want to change the repo path or model name → edit `config.py` only.

## Setup

1. **Install dependencies**
   ```bash
   pip install -r requirements.txt
   ```

2. **Get a free Groq API key**
   Sign up at https://console.groq.com/keys — it's free and takes a minute.

3. **Configure**
   ```bash
   cp .env.example .env
   ```
   Then edit `.env`:
   - `GROQ_API_KEY` → paste your key
   - `REPO_ROOT` → the folder you want to search (e.g. your `axe` project)

   You can also just edit `ROOT_DIR` directly in `config.py` instead of
   using the environment variable — either works.

4. **Run it**
   ```bash
   python main.py
   ```
   First run will ingest + embed the repo and save the index to
   `index_store/` (so the next run is instant). If you change the repo's
   code later, re-run with:
   ```bash
   python main.py --rebuild
   ```

5. **Ask questions**
   ```
   > How is brand derived in the ezcater transform?
   ```
   You'll get an answer plus the file(s) it was based on.

## Notes for a first RAG project

- **Embedding model** (`BAAI/bge-small-en-v1.5`) runs locally on your
  machine — no API key needed for search itself, only for the final
  answer-generation step.
- **FAISS** just finds "which stored vectors are closest to my query's
  vector" — it doesn't understand text, it only does math on numbers.
- **Groq** isn't itself an open-source *model* — it's a company that
  runs open-source models (like Llama 3.1) on very fast hardware and
  gives free API access. That's the "open source" piece you asked for.
- **No Docker here** — Docker in the reference project you found exists
  purely for *deploying* that app to Hugging Face Spaces (packaging
  Python + system libraries into one reproducible container). Since
  you're running locally, you don't need it. If you later want to put
  this on a server somewhere, that's when Docker becomes useful.

# Repo RAG — ask questions about your codebase

A small, file-per-concern RAG project: it reads your repo, splits Python
files into function/class-level chunks, embeds them, and lets you ask
questions in plain English. Answers are generated by an open-source LLM
(Llama 3.1, served via Groq's free API) and grounded in the actual code
retrieved.

## How the pieces fit together

```
config.py        <- edit settings here (repo path, model names, etc.)
utils.py           -> tiny shared helpers (safe_read_file)
ingest.py           -> walks the repo, splits files into chunks
embed_index.py       -> turns chunks into vectors, builds/saves/loads the FAISS index
search.py             -> given a query, filters (layer + file-name alias) + finds closest chunks
context.py             -> re-reads the FULL source file for each retrieved chunk
llm.py                   -> sends that context + query to Groq, gets back an answer
rag_agent.py               -> combines search.py + context.py + llm.py into one ask() call
main.py                      -> CLI you can run directly
backend.py                    -> FastAPI wrapper around rag_agent (for the web UI)
app.py                          -> Streamlit chat UI that talks to backend.py
```

If you want to change *what* gets indexed → edit `ingest.py`.
If you want to change *which* LLM answers → edit `llm.py` only.
If you want to change the repo path or model name → edit `config.py` only.
If you want to change how much context the LLM sees → edit `context.py`.

## Bug fix: file filtering wasn't working

`_extract_filters()` in `search.py` used to build its filters dict with
a `"file_name"` (singular) key, but only ever *wrote* to `"file_names"`
(plural) once it found an alias match. `_filter_chunks()` checked the
singular key — which was never touched — so the file-name filter was
silently ignored and every search fell back to plain embedding
similarity across the *entire* repo. That's why the separated project
sometimes pulled in chunks from the wrong file even when your notebook
got it right. Fixed by using `"file_names"` (a list) consistently.

A second contributor: the notebook re-read each matched chunk's *full
source file* for context (`get_context`) and used the larger
`llama-3.3-70b-versatile` model. The first pass at the modular version
only sent the isolated function-level chunk and defaulted to the
smaller `llama-3.1-8b-instant`. Both are now fixed — `context.py`
rebuilds full-file context and `config.py` defaults to the 70b model.
